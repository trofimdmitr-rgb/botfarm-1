## 1. Что это и зачем

**BotFarm** — один Telegram-бот + Telegram Mini App, на котором работает онлайн-запись для
**множества** малых бизнесов сразу (мастера маникюра, барберы, репетиторы, массажисты, автосервисы).

- Владельцы платформы — **Антон и Дмитрий (суперадмины)**. Только они создают бизнесы.
- Каждому бизнесу они выдают:
  - **ссылку для клиентов** — клиент видит только этот бизнес: услуги, цены, портфолио, запись;
  - **приглашение владельца** (одноразовое) — кто откроет первым, становится владельцем бизнеса.
- Предприниматели находятся холодной рассылкой, сервис для них **бесплатный**.
- Поэтому вся инфраструктура обязана быть **бесплатной** и держать ~1000+ активных пользователей в месяц.

Историческая основа — старый бот записи к мастеру маникюра на Python (aiogram + SQLite).
Его логику перенесли в TypeScript и исправили баги: прошедшие слоты, двойные записи, услуги без
длительности, потерю состояния при перезапуске, падения Markdown на именах с `_` и `*`.

## 2. Роли

| Роль | Как определяется | Что может |
|---|---|---|
| Суперадмин | Telegram ID есть в таблице `platform_admins` (или в env `SUPERADMIN_IDS`) | Всё: создавать, блокировать, удалять бизнесы, заходить в любой как админ |
| Владелец (`owner`) | строка в `business_admins` с role=owner (появляется по приглашению) | Управлять своим бизнесом, делать рассылку, приглашать помощников |
| Админ (`admin`) | `business_admins` с role=admin | Управлять бизнесом, но без рассылки и без удаления админов |
| Клиент | любой пользователь Telegram | Видит только бизнес, по ссылке которого пришёл |

Проверка прав — на сервере, в `server/rpc.ts → dispatch()`. Каждый метод помечен `need: user | admin | owner | super`.
**Фронтенду не доверяем**: скрытая кнопка — это не защита, защита — проверка в `dispatch`.

## 3. Стек и почему он такой

| Что | Чем | Почему |
|---|---|---|
| Хостинг | **Vercel Hobby** (бесплатно) | Нет сервера, нечему падать, автомасштабирование, деплой из GitHub |
| База | **Supabase Free**, Postgres | Бесплатно, настоящий Postgres: нужен для защиты от двойной записи (exclusion constraint) |
| Бот | **grammY** через вебхук | Работает в serverless, нет long-polling процесса |
| Mini App | **Vite + React**, без UI-библиотек | Маленький бандл (~90 КБ gzip), цвета из темы Telegram |
| Даты | **luxon** | Часовые пояса бизнеса (`Europe/Samara`, …) |
| Тесты | **vitest + PGlite** | PGlite — Postgres в памяти, тесты гоняются без интернета и без Supabase |

Все API — **одна** serverless-функция `api/index.mjs`: Vercel Fluid переиспользует тёплый
экземпляр, меньше холодных стартов и меньше расход лимитов. Маршруты: `/api/rpc`, `/api/bot`,
`/api/cron`, `/api/photo`, `/api/setup`, `/api/health` (через rewrite в `vercel.json`).

## 5. Ключевые решения (не ломать!)

1. **Защита от двойной записи — в БД**, ограничение `bookings_no_overlap` (`exclude using gist`,
   нужно расширение `btree_gist`). Не заменять проверкой в коде — при одновременных нажатиях она не спасёт.
   При конфликте `store.createBooking` пробует следующего свободного мастера, иначе `BookingConflict`.
2. **Время хранится в UTC (`timestamptz`)**, рабочие часы мастера — строки `"10:00"` в часовом поясе
   бизнеса (`businesses.timezone`). Всё пересчитывается через luxon в `slots.ts`.
3. **Доступность считается на сервере** (`store.availability`) и **перепроверяется** при записи.
4. **Авторизация Mini App** — заголовок `x-init-data` с `Telegram.WebApp.initData`, подпись
   проверяется в `auth.ts`. Без валидной подписи — 401. Никаких своих логинов/паролей.
5. **Фото портфолио хранятся в Telegram**: бот отправляет фото админу, сохраняем `file_id`,
   отдаём через `/api/photo` с долгим CDN-кэшем. Хранилище Supabase не тратится.
6. **Сообщения бота — HTML с `esc()`**, не Markdown.
7. **Секреты вебхука и cron выводятся из BOT_TOKEN** (`config.derived`) — меньше переменных окружения.
   В адрес вебхука добавлена метка `?v=…`: после смены токена адрес не совпадёт, и бот перенастроится сам.
8. **Самонастройка бота**: при первом запросе к продакшену (`/api/health`) сервер сам ставит вебхук,
   команды, кнопку меню. Ничего руками в BotFather настраивать не надо.
9. **Суперадмины — в таблице `platform_admins`**, кэшируются на 60 с. Добавить: `insert into platform_admins(tg_id, note) values (…)`.
10. **Напоминания**: Vercel Hobby разрешает cron только раз в сутки (`vercel.json`, 15:00 UTC = вечер по Москве/Самаре)
    → «завтра в …». Для «за 2 часа» — `db/002_pg_cron.sql`. `runReminders` идемпотентна.

## 7. Подводные камни деплоя (важно!)

1. **`api/index.mjs` — собранный файл, его коммитят.** После ЛЮБОЙ правки в `server/` выполнить
   `npm run build:api` и закоммитить `api/index.mjs`. Иначе на Vercel уедет старый сервер.
   (Сделано так, потому что Vercel ненадёжно собирает TS-функции с импортами `.js`. Можно улучшить,
   но только проверив деплой.)
2. **Vercel Hobby блокирует сборку, если автор коммита ≠ владелец аккаунта Vercel.** Коммить только
   от GitHub-аккаунта, привязанного к Vercel. **Не добавлять** строки `Co-Authored-By:` — из-за них сборка
   получает статус *Blocked*.
3. Кнопка Redeploy в интерфейсе Vercel на Hobby может требовать Pro — передеплой делать пустым коммитом:
   `git commit --allow-empty -m "redeploy" && git push`.
4. **Два деплоя на один бот = война вебхуков.** Каждый продакшен переставляет вебхук на себя.
   После переезда старый проект на Vercel удалить (или убрать в нём `BOT_TOKEN`).
5. Свой адрес сервер берёт из `PUBLIC_URL` → `VERCEL_PROJECT_PRODUCTION_URL` → из запроса к основному домену
   `<проект>.vercel.app` (`isProductionHost`). Проверить, что определился верно: `/api/health` → поле `publicUrl`.
6. Пулер Supabase (порт 6543, transaction mode) не поддерживает prepared statements — в `db.ts` стоит
   `prepare: false`, не убирать. Прямое подключение `db.<ref>.supabase.co` — только IPv6, с Vercel не работает.
7. Функции Vercel в регионе `fra1` (`vercel.json`) — рядом с Supabase `eu-central-1`. Новый проект Supabase
   создавать тоже в Frankfurt (eu-central-1), иначе каждый запрос будет медленнее.
8. **Секреты не коммитить и не писать в чаты.** Только в Environment Variables на Vercel.

## 8.5. MAX (второй мессенджер)

Тот же сервер и тот же деплой на Vercel, отдельный вебхук `/api/max`. Включается сам, когда в Environment Variables
появляется `MAX_BOT_TOKEN` (дальше — передеплой и запрос к `/api/health`: сервер подпишет вебхук, задаст команды).

- **Пользователи MAX — в тех же таблицах с ОТРИЦАТЕЛЬНЫМ id** (`−user_id` из MAX). По знаку id `tg()` решает, куда слать
  сообщение (`server/telegram.ts`), кнопки Telegram переводятся в кнопки MAX (`btnsFromTelegram` → `maxKeyboard`).
- Логика ответов бота общая: `server/flows.ts` (Telegram — `bot.ts`, MAX — `maxbot.ts`).
- API: `platform-api2.max.ru`, токен в заголовке `Authorization`; сертификат Минцифры встроен (`server/max-ca.ts`, до 2032).
- Вебхук защищён секретом `X-Max-Bot-Api-Secret` (производный от токена). Отвечать 200 всегда: иначе MAX повторяет и через 8 ч отключает.
- Мини-апп: в кабинете MAX адрес `https://<домен>/?max=1`. Подпись initData — тот же алгоритм, ключ — токен MAX
  (заголовок `x-max-init-data`). Параметр запуска `?startapp=<slug>__<view>` (только `[A-Za-z0-9_-]`).
- В MAX нет темы, нижней кнопки и окон alert/confirm — в приложении своя кнопка и своё окно (`inAppDialog`).
- Фото хранятся в Telegram: фото от мастера из MAX уходят в `TG_STORAGE_CHAT_ID` (по умолчанию — первому суперадмину).
- Суперадмин в MAX: в боте MAX команда `/id` → `insert into platform_admins(tg_id, note) values (-<id>, 'Антон MAX')`.
- Ссылки: клиентам `https://max.ru/<бот>?startapp=<slug>`, панель `?start=adm_<slug>`, приглашение `?start=inv_<код>`.
- Тесты: `tests/max.test.ts`, `e2e/max.spec.ts`.
- **Один человек в двух мессенджерах** (`server/links.ts`, таблица `link_requests`, поля `users.phone/person_id`):
  когда аккаунт указывает номер (запись или «поделиться номером»), аккаунты с тем же номером в ДРУГОМ мессенджере
  связываются сразу (решение Антона — без подтверждения), во второй мессенджер уходит оповещение с кнопкой «Это не я»
  (разрывает связь навсегда для этой пары). Связанные видят записи друг друга (`store.samePerson`), уведомления клиенту
  идут во все его мессенджеры (`notify.toClient`). Нет аккаунта во втором мессенджере / MAX не подключён — ничего не шлём.
  Схема догоняется сама: `db/003_links.sql` выполняется при каждом холодном старте (`MIGRATIONS_SQL`).
  Бот не может написать первым тому, кто его не запускал (правило Telegram и MAX), поэтому: при первом /start клиенту
  предлагается «Поделиться номером» (`flows.contactAsk`; в Telegram — клавиатура request_contact, в MAX — кнопка
  request_contact) → связка сразу и ответ «Нашли ваш аккаунт…» со списком записей; а в «Вы записаны» — ссылка
  «Получать напоминания и в MAX/Telegram», пока во втором мессенджере аккаунта нет. Принимаем только СВОЙ контакт.

## 10. Правила для агента

- Не ломай пункты раздела 5. Если очень нужно — сначала объясни, зачем.
- Любая новая серверная логика — с тестом в `tests/` (смотри `tests/rpc.test.ts` как пример: `setDb(PGlite)`, `setSender(mock)`).
- Права проверяй в `dispatch` по полю `need`, а не на фронте.
- Новые поля бизнеса — в `BusinessSettings` (`templates.ts`) + дефолт в `baseSettings` + сохранение в `rpc.saveSettings` (белый список ключей `SETTINGS_KEYS`).
- Изменения схемы БД — новым файлом `db/003_….sql` (идемпотентно: `if not exists`), и продублировать в `001_init.sql` для чистой установки (тесты используют `001_init.sql`).
- После правок сервера — `npm run build:api` и коммит `api/index.mjs`.
- Коммиты — от владельца аккаунта Vercel, без `Co-Authored-By`.
- Не добавлять платные сервисы и тяжёлые библиотеки. Бандл Mini App держать < 150 КБ gzip.
- Секреты — только в env Vercel, никогда в код, коммиты и чаты.
